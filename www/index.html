Self-hosted sandboxes · Go · Docker + gVisor

Run untrusted, AI-generated code on your own hardware.

openblox is under 3,000 lines of Go over Docker and gVisor. No control plane, no database, no scheduler — a sandbox is a container, and the container is the state.

For teams running code an LLM wrote against files a user uploaded, who would rather that workload stayed on hardware they own than crossed someone else's boundary.

Restrictive by default the zero value of every option is the most restrictive one 
// No options. This is the entire configuration.
sb, err := backend.Create(ctx, "session-1",
    sandbox.WithImage("ghcr.io/blox-eng/openblox-sandbox:latest"))
  • IsolationgVisor (runsc) — syscalls served in user space, not by the host kernel
  • NetworkNo external interface, so no egress and no DNS side channel
  • FilesystemRead-only root, non-root user (root is refused), noexec scratch
  • ResourcesBounded CPU, memory (no swap), disk, process count and captured output
  • PrivilegesAll capabilities dropped, no-new-privileges
  • LifetimeCommands killed at their timeout; sandboxes reaped when idle and at max age

If the host cannot provide gVisor, Create fails with ErrRuntimeUnavailable. It never falls back to a weaker boundary. These are isolation measures, not a guarantee: the boundary is gVisor's, and THREAT_MODEL.md lists what is defended, the test behind each claim, and what is not.

Guarantee

The same guarantee, at two strengths.

Every isolation measure above can be relaxed. What changes between the library and the daemon is not whether it can be relaxed, but who is allowed to ask. Here is one relaxation — unrestricted egress — written identically against both.

Tier one · the library

backend, err := docker.New()

sb, err := backend.Create(ctx, "session-1",
    sandbox.WithImage(img),
    sandbox.WithEgress(sandbox.EgressUnrestricted),
)

Accepted — and visible. Your code chose it, at a call site one grep away. Nothing is hidden in a config file you forgot you wrote.

Tier two · through openbloxd

client, err := brokerclient.New(sock)

sb, err := client.Create(ctx, "session-1",
    brokerclient.WithProfile("code-exec"),
    sandbox.WithEgress(sandbox.EgressUnrestricted),
)
// invalid argument: egress is daemon policy
// and cannot be set per-request

Refused — and unreachable. A caller names a profile. It cannot name an image, a runtime, a user, an egress policy or a resource cap; those live in the daemon's config file, where no request reaches them.

That is the difference between weakening being visible and weakening being unreachable, and it is the whole reason the daemon exists.

Layer

The layer below a sandbox platform, not a smaller one.

your scheduler, your tenancy, your API yours to build, if you ever need it
openblox isolation, done correctly
Docker + gVisor the boundary itself

One rule decides what belongs here:

How a sandbox is isolated is openblox's problem. Which sandbox runs where is yours.
openblox's
Egress, capabilities, filesystem, resource caps, lifetime, runtime.
Yours, and not planned
Placement, queueing, tenancy, metering, snapshots.

Build those on top when something actually asks for them. That is what a lower layer is for, and it is why there is no control plane to adopt first. The comparison is libvirt, not OpenStack.

Quick start

A running sandbox in a dozen lines.

Needs Linux, Docker, and gVisor registered as the runsc runtime — how to register it. 

go get github.com/blox-eng/openblox
backend, err := docker.New()
if err != nil {
    return err
}
defer backend.Close()

// No options: no network, non-root, read-only rootfs, capped
// CPU/memory/PIDs, gVisor runtime, reaped when idle.
sb, err := backend.Create(ctx, "session-1",
    sandbox.WithImage("ghcr.io/blox-eng/openblox-sandbox:latest"))
if err != nil {
    return err
}

res, err := sb.Exec(ctx, sandbox.Command{
    Argv: []string{"python3", "-c", "print(6 * 7)"},
})
fmt.Println(string(res.Stdout)) // 42

That image is the reference sandbox userland; any image meeting the contract works.

One caveat before production: importing the library means your process holds the Docker socket, which is root-equivalent on the host. Run the openbloxd daemon there instead — it owns the socket, and your application talks to it over a Unix socket with the same Backend interface and no Docker access. Running in production covers deployment, verification, compatibility and upgrades.

Limits

When not to use it.

None of these are gaps waiting to be filled. Most are placement rather than isolation, which the rule above puts on your side of the line; the rest are trades made deliberately.

  • You need tenants isolated from each other at the API. Every caller of one openbloxd can reach every sandbox; tenancy is yours to enforce in front of it.
  • You need a fleet. One host, one daemon. No scheduling, no fairness.
  • You need a separate kernel per workload (hardware virtualisation), or protection from side channels between co-resident sandboxes.
  • You need snapshots, fork, pause/resume, or sub-second cold starts.
  • You cannot run Linux with gVisor, or cannot keep runsc patched.
